## Formal model and proof obligations

Use a small Lean 4 model of the workbook contract, not a model of XLSX internals or of the whole authoring service. Reuse the repository’s existing Lean 4.19.0 toolchain pin and Lake conventions from verification/lean/sat-access-code-start; create an isolated project at verification/lean/sat-import-template. Prefer Lean core and decidable finite-list properties; add no dependency unless a concrete proof requires it.

The model should define:

- Ordered sheet names and visibility; the optional active-sheet index.
- The ordered Questions headers.
- Six module records with stable label, section, and expected slot count.
- Template version and the abstract validation-list/taxonomy-range contract.
- Cell kinds for generated guidance content, distinguishing text from formula and embedded picture.
- A question-row contract with the parser-relevant fields: module, order, prompt, section-valid domain/skill, response type, difficulty, and pretest status.
- A module import predicate reflecting the documented parser boundary: exact question count, unique in-range order values, valid required fields, and exactly two pretests.

Do not encode every parser implementation detail in Lean. Keep the abstract predicate reviewable and map each clause to the corresponding parser check. Preserve normalization/alias behavior only if the stated claim depends on it. Parser error handling, ZIP resource limits, content compilation, and image byte handling remain Go implementation obligations.

Planned theorem statements, to be printed and checked exactly before proof:

1. Contract shape: the abstract template has exactly the five specified sheets in the specified order; _SAT is hidden; the Questions header vector is exact; the version is 2.
2. Slot arithmetic: module counts are exactly 27, 27, 27, 22, 22, 22 and sum to 147; adding the header yields 148 Questions rows.
3. Validation references: all modeled list ranges target the intended rows/columns and the Skill list references the modeled _SAT taxonomy range.
4. Guidance safety: all generated Guide and AI Instructions cells in the model have text kind and no picture or formula kind.
5. Blank rejection: a generated blank slot set cannot satisfy the modeled import predicate, with the failure derived from required question content and module/pretest requirements.
6. Complete fixture acceptance: a fixture with all six modules, required valid fields, unique in-range orders, exact counts, and exactly two pretests per module satisfies the modeled import predicate.
7. Optional P1 active sheet: when enabled, the active index resolves to AI Instructions while the sheet vector and order remain unchanged.

The theorem suite must not assume its target invariant as a precondition. Include initiation and preservation only if a state-transition model is actually introduced; this feature’s core contract is a finite immutable workbook description, so an invented transition system would add no assurance. The blank/complete theorems must use concrete fixture data or explicit decidable predicates, not a premise that already states the conclusion.

Assert required guidance content and absence of unexpected generated media. Exercise the resulting workbook through ParseSATWorkbook.

The required Go cases are:

1. Generated blank workbook parses as a preview with 147 input slots and is invalid.
2. A completed fixture based on the generated workbook, with six modules, correct counts, required fields, valid taxonomy/response shapes, and two pretests per module, parses valid.
3. Removing a required prompt or pretest, duplicating an order, using a section-incompatible taxonomy/response, or adding a Questions formula makes preview invalid.
4. Guidance text containing XML-sensitive characters, Unicode, backslashes, and line breaks round-trips to the same cell value.
5. A formula or picture inserted into a guidance sheet is absent from generated output; a picture outside Assets or outside Assets column D is rejected by the existing parser.
6. The P1 active sheet, if implemented, opens on AI Instructions without changing sheet order or _SAT visibility.
7. Existing authenticated download, preview, replacement-confirmation, and stale-revision conflict scenarios continue to pass. These demonstrate regression behavior, not a new formal proof of the unchanged flow.

Use a manual Excel-compatible viewer smoke check for readability and active-sheet behavior, because XML validity and Excelize reopening do not establish identical behavior in every spreadsheet application.

## Hostile cases and counterexamples to retain

- Empty prompt in one otherwise prefilled row: row is omitted from parsed questions and module count becomes invalid.
- Duplicate order within one module: unique-order condition fails even when total row count is correct.
- Incorrect pretest count in a module: preview remains invalid.
- Formula in Questions: preview blocks formula-bearing workbook.
- Image anchored outside Assets column D: parser reports a blocking placement issue.
- XML-sensitive text or line breaks in the long prompt: serialization/reopen mismatch must fail the round-trip check.
- Prompt exceeds a conservative cell-text budget: content assertion fails before release.
- Stale draft revision during commit: existing conflict behavior must remain; the feature does not weaken the current check.
- External AI fabricates an answer, taxonomy, module, or figure: application/formal model cannot prevent this. The prompt and Guide can require uncertainty reporting and human verification, but this remains a documented residual risk.

Do not add synthetic race schedules for the workbook generator. It is deterministic and introduces no shared mutable state; commit-race correctness belongs to the unchanged existing import flow and its regression tests.
