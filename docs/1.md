## 2. Findings

### Bug 1 (high): recoverable-looking provisional drafts are rejected after engine replacement

**Locations:** \60src/shared/durability/DurableResponseEngine.ts\60: \60acceptResponse\60 426–481, \60persistAcceptedResponse\60 504–553 / 617–651, \60isPendingResponseState\60 155–170, \60loadRecoveredPending\60 1069–1115; \60src/components/student/providers/StudentAttemptProvider.tsx\60: engine lifecycle 424–571 and projection 357–418.

**Evidence: directly probed, high confidence.** Three fresh-engine recovery tests lost the newest text: immediate teardown before initialization, immediate teardown after a completed initial recovery, and teardown while an initial snapshot was pending even after the fallback durable-store write completed. The checkpoint existed with the correct answer and \60clientVersion: 0\60; fresh recovery returned no visible response.

A real-provider probe made the user-facing rollback concrete:

\60\60\60text
hold the initial response snapshot open
persistAnswer(q1, "student latest") → visible "student latest"
rerender the same attempt with controlEpoch 1 → 2
replacement snapshot returns q1 = "server old"
observed visible answer: "server old"
local checkpoint still contains: "student latest", clientVersion: 0
\60\60\60

**Mechanism:** every acceptance first checkpoints version zero. A positive version is allocated only after asynchronous storage and recovery. Destruction aborts that allocation. The reader accepts positive versions or explicitly blocked drafts, but silently excludes ordinary unblocked zero-version records from **both** checkpoint and durable-store recovery. The replacement engine can then publish the old server value. Re-checkpointing after version allocation repairs the later window, not this earlier one.

**Reachability:** startup/reconnect with slow storage/snapshot, teardown/reload, and epoch changes during acceptance. This is not merely a hypothetical provider remount: the engine effect depends on \60attemptSnapshot.controlEpoch\60, and an ordinary proctor warning increments that epoch (\60backend/go/internal/proctor/service.go:430\60). A real incident's timing remains unknown. Healthy, already-versioned pending writes are not all lost; the defect concerns the provisional window.

**Impact:** latest answer/revision disappears from recovered visible state and is not sent, even though a browser record remains. The unsaved interval can include the initial snapshot's 15-second timeout, plus storage/recovery latency. Existing records may remain salvageable on the device; “not recovered by the app” is not the same as proven physical deletion.

**Smallest correct direction:** distinguish a durable **unversioned intent** from a **sendable command**. Recover and display the intent, then seed/allocate a legal version; preserve control/lease fences and show blocked/recovery choices where required. Do not simply allow zero onto the network or through the existing server-version comparison. Add fresh-instance tests, including provider epoch replacement—not just same-instance \60updateEpochs\60 tests or assertions that a storage write occurred.

### Bug 2 (high): writing reconciliation uses text length as freshness and poisons the teardown draft

**Locations:** \60src/components/student/StudentWriting.tsx\60: \60readLiveDraftForTask\60 195–203, \60commitEditorDraft\60 254–264, hydration effect 351–385, unmount cleanup 387–400; debounce 42 / 243–249. Textarea is uncontrolled at \60src/components/student/StudentWritingPanes.tsx:268–290\60.

**Evidence: directly probed in jsdom and Chromium, high confidence.** Start with \60old long answer\60, focus the editor, replace it with \60new\60, rerender with a fresh object still containing the old value, then unmount before 300 ms. DOM showed \60new\60 immediately before unmount, but **zero** writing-change commits were made; persisted parent answer remained \60old long answer\60. Ordinary fill → blur was a passing control.

**Mechanism:** when focused, a longer incoming value replaces \60liveDraftsByTaskRef\60 without changing the textarea. During passive unmount cleanup the editor ref is null, so commit falls back to that overwritten live ref. It equals the previously committed old value, suppresses \60onWritingChange\60, and clears the pending timer. The same heuristic also picks an equal-length stale value when unfocused: a focused-independent component probe changed \60OLD → NEW\60, rerendered \60OLD\60, and observed the DOM revert to \60OLD\60 before the pending commit.

**Reachability:** edge lifecycle sequence: deletion/shortening, same-task stale props during the 300 ms commit window, then unmount/layout/module/route removal without an earlier successful blur/explicit draft commit. The focused/unmount case used real browser editing. The unfocused synthetic-change case is supplemental component evidence, not a claim that ordinary keyboard typing occurs unfocused. Live-writing registration in \60StudentApp.tsx:652–656\60 only updates a ref; it is not an independent durability write.

**Impact:** revisions that shorten text—including clearing an answer—are less protected than appends. Word-count/preview and DOM can temporarily describe different drafts. Extending the debounce would enlarge the vulnerable window.

**Smallest correct direction:** preserve dirty local intent by explicit task identity and revision/acknowledgement, never by string length. Retain an immutable last-native-edit snapshot for teardown and commit that exact snapshot before cancelling the timer. Test append, delete-to-empty, shorter, same-length replacement, stale props, blur, unmount and acknowledgement of an older edit.

### Bug 3 (medium): native-only objective edits can be reset before the rescue hook saves them

**Locations:** \60src/components/student/ProtectedInput.tsx\60: reset effect 57–77, native listeners 130–143, lifecycle rescue 214–238. Example shipped caller: \60src/components/student/QuestionRenderer.tsx:308–312\60.

**Evidence: directly probed, high confidence in the mechanism; native browser occurrence is unverified.** Inject \60base native only\60 into the real controlled input without a React change callback, emit native input, trigger an unrelated parent render, then blur. Chromium and jsdom ended with DOM/state \60base\60. The test deliberately injects the missing-React-change condition; it does not prove Safari spontaneously drops that event.

**Mechanism:** native input only caches/optionally publishes a live value. React can restore the older controlled prop during rerender. The effect treats a changed \60onChange\60 function as hydration and resets its rescue snapshot from the now-old DOM. Blur/lifecycle handlers likewise re-read the already-reset input. Some adapters, including cloze, do not supply an independent live-value callback. The rescue code therefore does not cover the very DOM-ahead-of-React interleaving it documents.

**Impact / reachability:** conditional loss before autosave ever receives the answer; relevant to native/IME/autofill/lifecycle edge events, not proven for normal React \60onChange\60 delivery.

**Smallest correct direction:** feed real native intent into one idempotent answer owner early, and retain it until the matching controlled revision acknowledges it. Callback identity is not hydration identity. Test a rerender between native input and blur/pagehide, including an empty value, then validate on the affected physical browser.

### Bug 4 (medium): focused task navigation can commit Task 1's DOM as Task 2's answer

**Locations:** \60src/components/student/StudentWriting.tsx\60: external task sync 337–349, focused hydration early return 362–368, blur commit 556–567; \60src/components/student/StudentWritingPanes.tsx:268–290\60.

**Evidence: directly probed in jsdom and Chromium.** With \60task1 = old long answer\60 and \60task2 = second answer\60, type \60task one revised\60 into the focused first task. Change \60currentQuestionId\60 externally to Task 2 without blurring. The same textarea acquires \60data-task-id=task2\60 but keeps Task 1 text. Subsequent blur produced both commits:

\60\60\60text
[task1, "task one revised"]
[task2, "task one revised"]
\60\60\60

**Mechanism:** the unkeyed uncontrolled textarea survives the task change; focus protection skips installing the new task's value, while commit callbacks now use the new task ID.

**Impact / reachability:** entire second-task answer can be overwritten if navigation occurs without a prior blur. This is a conditional component contract defect: ordinary Task 2 button clicks passed in Chromium, and global keyboard navigation has editing-target guards. Do not infer that every task switch currently fails or claim physical iPad button behavior was tested.

**Smallest correct direction:** commit under the old task identity, then atomically reset/key the editor and all focus/snapshot refs for the new identity. Never apply same-task typing protection across task identity changes. Assert both tasks' values after external navigation, another keystroke, blur and save.

### Bug 5 (medium): “Saved” can remain visible while a new intent is awaiting version initialization

**Locations:** \60src/shared/durability/DurableResponseEngine.ts\60: default status 297, \60getPendingCount\60 349–350, acceptance 468–501, delayed status transition 631–635; \60src/components/student/providers/StudentAttemptProvider.tsx:371–418,490–505\60; \60src/components/student/StudentApp.tsx:174–179\60; \60src/components/student/StudentHeader.tsx:475–480\60.

**Evidence: directly probed through actual provider/runtime.** During the held initial snapshot, visible answer was \60student latest\60, provider pending count was **1**, and runtime status remained **saved**. Engine-only probe after local persistence still reported \60synced\60 and queue count **0**, despite a visible pending draft.

**Mechanism:** accepting a provisional value updates response state but not sync status; queue count excludes acceptances not yet put in the outbox. A previously saved UI state survives until version allocation reaches the later status update.

**Impact / reachability:** ordinary slow startup/recovery/storage creates a false durability signal, magnifying Bug 1. This finding assumes a previou s saved state; it does not claim every initially idle attempt immediately displays Saved.

**Smallest correct direction:** move to a pending/saving state synchronously when accepting intent; derive unsaved status from pending intent plus in-flight/outbox work, not queue length alone. Only a matching acknowledgement may restore server-saved truth. Test with a snapshot/storage promise held unresolved and a prior saved state.

### Bug 6 (medium): reconnect batches can exceed the server's hard command limit

**Locations:** \60src/shared/durability/DurableResponseEngine.ts:1395–1414\60 (copies every sendable outbox entry into one request), retry path 1508–1527; \60backend/go/internal/attempts/validate.go:16,58–59\60 (100-command cap).

**Evidence: directly probed client boundary + executed Go validator test + static cross-boundary conclusion.** Accumulate and flush 100 different questions: emitted batch sizes \60[100]\60. At 101: \60[101]\60, violating the independent server limit. The probe echoed acknowledgements only to end the run; it did **not** assert that the actual Go server accepted that oversized batch. Go's existing oversized-envelope test passed, confirming rejection.

**Mechanism / impact:** no chunking by command count; server rejects the whole envelope before any mutation. Generic retries requeue the same oversized set instead of reducing it, stranding otherwise valid locally retained answers. This is a delivery stall, not immediate visible text deletion.

**Reachability:** long offline/backlogged attempts with over 100 question aggregates (shared engine supports other exam providers and custom content). Not established as an ordinary standard IELTS-paper trigger. Request byte limits are another static boundary worth testing: handler body cap is 256 KiB (\60backend/go/internal/platform/httpx/httpx.go:42\60), while the client does not size batches by encoded bytes.

**Smallest correct direction:** chunk sendable work by command count **and encoded body size**, retain per-command acknowledgements/retry identity, and ensure a permanently invalid command cannot block valid neighbors. Regress 99/100/101 and just-below/at/above byte limits.

## 5. The single most valuable next pass

**Repair provisional-intent recovery and prove it through provider replacement first.** It directly reproduces visible rollback while typing and spans objective and writing persistence once values reach the engine.

Smallest safe acceptance contract:

1. Hold snapshot recovery open; accept a non-empty answer, then a shorter edit and an empty edit in separate cases.
2. Verify the newest intent has a durable local representation and UI cannot say server-saved.
3. Destroy/recreate immediately and after asynchronous storage completion; repeat on a same-attempt control-epoch refresh.
4. Restore the exact newest local intent as visible/pending, or explicitly blocked with its content preserved under the new control epoch—never silently fall back to the old server answer.
5. Seed a legal positive version only after recovery; never send zero or cross a lease fence automatically.
6. Delay/out-of-order the old snapshot and acknowledgement; prove they cannot replace newer typing.
7. Run the same contract with real IndexedDB, localStorage fallback, storage failure, and browser reload.

Do not replace this with “increase debounce,” “force a rerender,” or “always prefer longer text.” Those do not solve the ownership/version mismatch.
