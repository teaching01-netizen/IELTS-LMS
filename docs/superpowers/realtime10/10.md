# Implementation plan: SAT realtime Yjs/Hocuspocus to 10/10

This is an execution-ready plan only; no repository files were modified. It covers the audited bugs plus the cross-boundary races discovered around lifecycle, caching, revision acknowledgements, and partial cleanup.

## 1. Goal

Make SAT authoring collaboration correct across:

- Multiple browser tabs and concurrent authors.
- IndexedDB recovery and reconnects.
- Hocuspocus restarts.
- Publish, delete, replacement, and shutdown flows.
- Read-only authorization and lifecycle freezes.
- Yjs compaction and state-vector limits.
- Preview/release navigation.
- Go/MySQL persistence and revision materialization.

Out of scope:

- IELTS/non-SAT collaboration.
- Per-session Yjs rooms.
- A conflict-resolution UI for semantic field conflicts.
- First-class offline authoring beyond safe IndexedDB recovery.
- Replacing the existing rich-text editor or Yjs data model.

## 2. Current system understanding

Current flow:

```text
SAT UI
  ↓
workspaceProvider.ts / provider.ts
  ↓
Hocuspocus WebSocket + IndexedDB
  ↓
services/authoring-coedit
  ↓
signed Go private API
  ↓
MySQL binary state + materialized question/workspace projections
```

```text
Go marks rows `freezing`
  ↓
Hocuspocus `/control/freeze`
  ↓
Hocuspocus flushes through ordinary Go `/store`
  ↓
Go rejects stores while rows are `freezing`
```

## 3. Behavioral contract

The fixed system must guarantee:

1. MySQL is the durable source of truth for publish, reload, and restart.
2. The live Hocuspocus Y.Doc is the active merge source.
3. IndexedDB is a recovery cache, never an authority.
4. A browser is `Saved` only when its current state vector has a durable acknowledgement.
5. Ordinary stores are rejected during a durable freeze.
6. A dedicated final store may run only for the matching freeze operation.
7. Read tokens remain read-only through freeze, unfreeze, refresh, and reconnect.
8. Initial workspace seeding is server-arbitrated and single-writer.
9. Compaction is durably committed before it is exposed to clients.
10. A compacted room cannot merge an old cache blindly.
11. UI-only workspace changes do not increment question/materialized revisions.
12. Every accepted durable state change still has an ordering sequence for acknowledgements.
13. Preview/release navigation waits for the exact durable acknowledgement.
14. Failed freeze, publish, close, or delete operations leave no half-frozen writable room.
15. No lifecycle operation can release another operation’s freeze.

Target lifecycle:

```text
initializing → active → freezing → closed
                         ↘ active on abort/expiry
```

`freezing` is the durable write fence. The service’s in-memory frozen/read-only state protects the live room. Existing `frozen` rows remain fail-closed and require explicit reconciliation.

## 6. Design decisions

### Decision 1: Dedicated final-store path

- Reason: ordinary stores must remain forbidden during `freezing`.
- Change: add private `/internal/authoring-coedit/final-store`.
- Behavior: accepts only a matching `freezeOperationId`, verifies the previous hash, writes the final state, and leaves the row fenced.
- Rejected: allowing ordinary stores during `freezing`; that removes the lifecycle safety boundary.
- Protects: AT-05, AT-07, AT-09, AT-11.

### Decision 2: One operation ID across Go and Hocuspocus

- Reason: cleanup must be ownership-aware.
- Add: `freezeOperationId` and `freezeExpiresAt`.
- Rejected: an unscoped `ReopenActive`; an old request could reopen a newer freeze.
- Protects: AT-09, AT-10, AT-12.

### Decision 3: Server-owned workspace seeding

- Reason: local `fragment.length` and `root.has()` checks cannot arbitrate two clients.
- Change: clients send authenticated seed proposals; Hocuspocus applies at most one proposal per root under a keyed lock.
- Rejected: deterministic client IDs or client-only guards; they do not prevent concurrent local updates from merging.
- Protects: AT-02, AT-03.

### Decision 4: Durable compaction epoch

- Reason: a new compacted Yjs client identity cannot safely merge old IndexedDB history.
- Add: `stateEpoch`, incremented only after a successful durable rebase.
- Rejected: memory-only compaction; it produces false acknowledgements and stale-cache duplication.
- Protects: AT-13, AT-14, AT-15, AT-19.

### Decision 5: Separate commit sequence from materialized revision

- Reason: UI-only commits can share a materialized revision but still need ordered acknowledgements.
- Add: `commitSequence`.
- `materializedRevision` remains domain/projection revision.
- `commitSequence` orders every distinct durable Yjs state.
- Protects: AT-16 and AT-18.

### Decision 6: Navigation waits for durable acknowledgement

- Reason: Hocuspocus `destroy()` is best-effort and preview reads MySQL-backed projections.
- Change: flush provider buffers, await exact current-vector acknowledgement, then invalidate queries and navigate.
- Protects: AT-17.

## 9. Data/state lifecycle

```text
Room creation
  → Go creates initializing row
  → service loads durable state
  → server arbitrates first workspace seeds
  → final seed state is stored

Active editing
  → browser edits Y.Doc
  → Hocuspocus broadcasts updates
  → IndexedDB retains recovery copy
  → persistence store writes MySQL atomically
  → Go returns commit sequence/vector
  → service broadcasts acknowledgement

Compaction
  → service detects oversized state vector
  → rebuilds from durable projection
  → Go validates old hash/epoch
  → Go durably stores rebuilt binary
  → epoch increments
  → service applies rebuilt document
  → clients use epoch-aware cache

Publish/delete/replacement
  → Go begins owned freeze operation
  → service makes live rooms read-only
  → service final-stores loaded rooms
  → service reads durable state for unloaded rooms
  → Go verifies manifest transactionally
  → mutation commits
  → service closes rooms
  → Go closes rows

Failure/expiry
  → service rolls back local freeze where safe
  → Go aborts matching operation
  → expired durable freezes are recovered
  → divergent local cache remains exportable
```
