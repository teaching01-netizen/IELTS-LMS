# Our SAT exam-day and 10,000-student test plan

**Purpose:** Prove this product's SAT exam flow from entry through final answer submission while 10,000 distinct students are actively testing at once. This is a **plan, not a claim that the system already passes**. “100%” means every listed product behavior and every delivered answer has a recorded, passing assertion; a missing or untestable behavior is a release blocker. Scores and score accuracy are out of scope.

## 1. Product contract and server-owned time

The test oracle is this system's **pinned published exam version, schedule/runtime plan, server timestamps, and configured admission and completion rules**. The browser displays time but cannot grant time, restart a module, choose a branch, or declare a submission complete. Pin the runtime timing model for each run. For the current `cohort_section_v3` flow, the room's section/module windows are authoritative: a student who starts late receives the **remaining room window**, not a new full module duration. Pause and extension effects must come from the server. The default SAT blueprint can be used as a full-size fixture, but its durations and question counts are test data read from the published version, not external policy requirements.

| Stage | Required behavior in our exam |
| --- | --- |
| Entry | Authenticate the assigned student, create or resume one attempt, show the waiting state until the proctor/runtime starts, and reject another identity. Late entry follows the server's schedule policy. |
| Reading and Writing | Open Module 1 with its published question set and server window; at its server-owned end, open exactly the selected higher or lower Module 2. |
| Break | Use the published gap and runtime `nextSectionStartAt`; block closed-module editing while waiting for Math. |
| Math | Open Module 1, then exactly the selected higher or lower Module 2. Include multiple-choice and student-produced numeric responses in the fixture. |
| Timing | The server's module attempt, cohort section, pause, extension, and deadline determine what the student can do. Browser clock skew, reload, and reconnect must not add time. A late entrant receives only the server-computed remaining room window. |
| Finish | The server closes modules and terminalizes the attempt under the configured rules. Failed/offline saves and submission attempts must show their real pending/retry state; staff and student see completion only when it is durable. |

For the current default blueprint, the full-size fixture has 27 questions and 32 minutes per Reading and Writing module, 22 questions and 35 minutes per Math module, and a 10-minute gap: **98 delivered question slots and 144 minutes including the gap**. These values come from `src/features/exam-authoring/providers/sat/satProvider.ts`. Before each run, read the actual pinned version and runtime plan and derive all expected counts, durations, and branch IDs from those records. The authored pool includes both Module 2 branches; each student sees only one branch per section.

## 2. Pass/fail oracle: the student's answers are the result

For **every admitted student**, the harness records an independent, append-only action journal: `runId`, `scheduleId`, `attemptId`, `sectionId`, `moduleId`, `moduleAttemptId`, `examQuestionId`, action time, client write ID, response payload, server acknowledgement/revision, and expected final value. Keep full response values in a restricted test artifact; use hashes and IDs in normal logs. Pin the published exam version and the routing-policy revision before starting.

Build the expected final answer map from the **last server-acknowledged write for each delivered question before its module closes**, plus any answer entered before the deadline and later accepted from the offline outbox under the recovery policy. A visible local edit without an acknowledgement is tracked as `pending`, never quietly counted as saved. Preserve unanswered slots explicitly as `null`; do not confuse unanswered, an empty string, an omitted row, and a failed read. Compare exact canonical answer payloads (selected option ID or numeric text/value as accepted by the write API), without scoring or whitespace-normalizing away a difference. For answer changes, the final accepted version wins. Replayed write IDs must not create a second version.

After the terminal receipt exists, compare the journal with **both** the server's V2 response rows at the sealed answer revision and the authorized SAT result-detail response (or a read-only test verifier at the same revision if the detail API cannot expose every answer). Join by `attemptId + moduleAttemptId + examQuestionId`, never by display position or a reusable module key. Also assert:

- Exactly one attempt per admitted student. For each successfully submitted sitting, exactly one terminalization receipt, submission, and SAT result; all four refer to the same student, schedule, published version, and attempt. An explicitly pending sitting must remain visible as pending and never masquerade as submitted.
- Exactly the number of question identities in the student's pinned, selected modules (98 for the current default full-size fixture). Every expected answered slot matches **1:1** in storage and result detail; every expected unanswered slot is still represented as unanswered. No response from an unselected Module 2 branch appears.
- The sealed answer revision equals the revision used by the result; no later write changes a sealed answer. If this cannot be proved with the current result contract, mark the test **unverifiable/fail** until the revision is exposed to the verifier.
- Zero missing answers, extra answers, swapped candidate answers, duplicate question identities, duplicate results, or false “submitted” screens. A failed or unauthorized attempt must not produce a normal submitted result.

**Offline limit:** If a student makes an edit that never reaches the server and then permanently loses the device/browser data, no server-side test can reconstruct that edit. The report must classify that edit as unsynced/unrecoverable and compare the eventual result with the last server-acknowledged snapshot. It cannot claim the unsynced edit reached the result. The test must distinguish server-acknowledged answers from local-only edits.

## 3. Fixtures and environment

1. Use one production-shaped, isolated staging environment with the same API/worker topology, database class and indexes, cache, load balancer, TLS, rate limits, observability, and deployment settings intended for exam day. Record versions and capacity. Never run the 10,000-student rehearsal against a live exam.
2. Publish a complete SAT fixture with real-size content and pinned IDs. The current default blueprint provides 27-question Reading and Writing base/lower/higher modules, 22-question Math base/lower/higher modules, two pretest items per module, and a 10-minute gap. Read the **published** routing threshold, question set, and durations at runtime. Include Math numeric-entry, unanswered, changed-answer, and long-response edge values. Do not use the small three-question integration fixture as load proof.
3. Provision **10,000 unique student identities and attempts** across 400 rooms/schedules of 25 students, with assigned staff for each room. This models a full administration while keeping 10,000 candidates active simultaneously. Use a fresh run ID, schedules, and database state per rehearsal; prove that every identity resolves to one attempt. Include four adaptive combinations (higher/higher, higher/lower, lower/higher, lower/lower), 2,500 students each, with threshold-minus-one, threshold, and threshold-plus-one cases in both sections.
4. Use synchronized but independently monitored load generators. Verify the generators have spare CPU, memory, sockets, and outbound bandwidth; otherwise their saturation invalidates server measurements. Keep a small set of real Chromium browsers on the same run for UI, accessibility, and crash checks; API virtual users alone cannot prove browser behavior.
5. Capture a baseline before load: query plans, connection pools, worker lag, queue depths, DB locks/deadlocks, storage size, cache hit rate, process memory, error rates, proctor freshness, and response latency by endpoint. Preserve deployment and fixture hashes with the report.

## 4. Functional exam-day matrix

Each row needs an automated assertion on the student screen, canonical server state, and the answer oracle where applicable. Run on both higher and lower paths in Reading and Writing and Math; do not accept a route label without checking the selected **module ID and its question set**.

| ID | Scenario and injected condition | Required assertion |
| --- | --- | --- |
| E01 | Assigned student enters before start, completes check-in; proctor starts the runtime | One attempt; waiting screen before start; correct candidate and pinned exam; module opens only when the server allows it; displayed time matches the server snapshot/deadline. |
| E02 | Duplicate entry, refresh, second tab, stale or tampered candidate URL/cookie | Same authorized attempt or explicit denial; no duplicate attempt; another student's answers never render or save. Writer takeover follows the existing lease policy. |
| E03 | Student arrives just before runtime start, just after start, midway through Module 1, after its deadline, during the gap, and after completion | Apply this schedule's actual admission/resume rule. If admitted late, use only the remaining server-owned room/module window; an elapsed module has zero remaining and reconciles forward. If denied, create no active exam. Never grant a fresh full clock from arrival time. |
| E04 | Answer, clear, change twice, review, navigate away/back, mark for review, then wait for autosave | UI and server retain the last acknowledged answer, including null after clear. The durability state is observable to the test harness; no response is counted as saved before server acknowledgement. |
| E05 | Lose network for 10 seconds, 2 minutes, and across a module boundary; continue answering on the loaded page | Exercise the product's offline/outbox behavior: local actions remain queued and recover according to the configured policy; acknowledged answers stay safe. On reconnect, the server determines the active module and accepts or rejects queued writes by its own deadline. |
| E06 | Reconnect with delayed/reordered/duplicated responses, expired credential, 429/5xx, or a second writer | Bounded retry/backoff; idempotent writes; fresh credential/lease resolution; no answer rollback, cross-module write, retry storm, or false saved/submitted status. |
| E07 | Reload, close tab, force-kill browser process, reopen on same device, and recover after restart | Same attempt, current server-selected module/gap/completion state, prior acknowledged answers, and server-computed time. Apply only an actual server pause/extension; a crash itself must not mint extra time. Test immediately before and after save acknowledgement and while offline. A simple reload is not proof of crash recovery. |
| E08 | Reading and Writing Module 1 reaches its server deadline with answers below/at/above the published threshold | Exactly one route decision and one correct lower/higher Module 2 **ID**; only that branch's published questions shown; no return to Module 1; saved Module 1 answers unchanged. |
| E09 | Repeat E08 for Math Module 1, including student-produced answers | Correct lower/higher Math Module 2 ID and question set; no Reading and Writing response or Math unselected-branch response in the active set. |
| E10 | Reading and Writing Module 2 closes; enter/leave the configured gap; reconnect during it | Gap length and Math availability equal the server runtime plan; no editing closed modules; Math begins at the server-authorized point with the room-anchored clock. |
| E11 | Finish all questions before deadline; timer at 5 minutes, 1 second, and expiry; browser clock skew ±5 minutes | Review never triggers early terminalization; server deadline controls transition/submission; no repeated 0:00 loops, time reset, or extra seconds from refresh/reconnect. |
| E12 | Finish Math Module 2 online, submit response delayed/lost, retry/reload, or run worker and client completion together | Exactly one terminal receipt, submission, and result; same final answer map; same receipt/result on retry; student and proctor see submitted only after the durable terminal state. |
| E13 | Finish offline, then reconnect inside the product's configured recovery window; never reconnect; crash before pending outbox flush | Pending state and instructions match actual server policy; reconnect uploads eligible answers once and reaches the correct terminal state; permanently unavailable local answers are explicitly classified as unrecoverable rather than fabricated. |
| E14 | Proctor pause/resume, approved extra time, termination, or cancellation during an active module | Only authorized actions change state; timer and write rules follow the server; answer snapshots and terminal outcome remain tied to the correct student. Test these as policy variants, not as substitutes for the standard sitting. |
| E15 | Candidate absent/no answers, partial answers, or disappears in Module 1/last module | Server reaches the correct terminal/pending policy state without relying on another browser request; exact acknowledged answers and explicit unanswered slots survive. |
| E16 | Use question navigator, review flags, cross-out, highlights/notes, timer show/hide, Math calculator/reference sheet, and keyboard controls | Controls work only where permitted, survive recovery where intended, remain accessible, and do not alter answer payloads, routing, or timing unexpectedly. |

## 5. The 10,000-concurrent rehearsal

**Capacity definition:** 10,000 distinct admitted students with active attempts across the full **published server-timed sitting** (144 minutes including the gap for the current default fixture), plus staff monitoring, reconnects, saves, transitions, and submission. A one-minute 10,000-VU spike or 10,000 idle sockets does **not** meet this definition. Run at real time at least once; accelerated clocks are useful for regression but cannot certify the full sitting, expiry, or worker behavior.

| Phase | Load profile and proof |
| --- | --- |
| Entry wave | 10,000 check-ins over the configured arrival window, then a burst of 2,000 in 30 seconds. Exercise queue/`Retry-After` and re-entry; verify every eligible user gets one attempt and any late entrant follows the server's room-window timing. |
| Start and steady state | Staff start rooms; reach 10,000 simultaneously active students and hold through all published modules. Each student reads content, navigates/reviews, sends answer changes and heartbeats at measured UI cadence. Use the actual selected question count (98 for the default fixture), with deterministic answered/unanswered and answer-change patterns. Record active count every minute. |
| Fault wave | During each module, inject disjoint network loss (5%), browser restart (2% on the real-browser sample plus equivalent API session drop), 429/5xx retry (2%), and late arrival (1% separate from the 10,000 admitted cohort). Restore connectivity at staggered times to test backlog drainage. |
| Adaptive handoffs | Have the four route combinations cross Module 1 expiry in overlapping windows; assert decision ID = opened Module 2 ID = student bootstrap ID = proctor ID. Measure time from authoritative expiry to usable next module and count stalled candidates. |
| Gap and Math | Keep the full cohort active through the configured gap and Math. Verify room/proctor dashboards, server-backed student/module clocks, and retained responses throughout. |
| Submission wave | Complete in a realistic spread, then a separate worst-case burst of 2,000 finishes within 30 seconds. Include offline-at-finish students who later reconnect. Keep staff dashboards open. |
| Reconciliation | Wait for the documented terminalization/recovery window, then run the full 10,000-attempt answer comparator, duplicate checks, and pending/unrecoverable classification. No sampling for data integrity. |

Record throughput and p50/p95/p99/max latency for entry, bootstrap, active-module read, response ACK, reconnect, route handoff, proctor roster, and terminalization; also DB CPU/IO, locks, pool wait, deadlocks, worker lag, queue age, memory, GC, and generator health. Track one status per candidate (`not_entered`, `waiting`, `active`, `recovering`, `pending_submission`, `submitted`, `blocked`) so a successful HTTP rate cannot hide missing students.

**Proposed release gates** (freeze these before the run): all 10,000 eligible students admitted and observed active; 10,000/10,000 expected final states accounted for; 0 mismatched acknowledged answers; 0 duplicate attempts/submissions/results; 0 wrong adaptive module IDs; 0 cross-student data; 0 silently lost pending answers; 0 client-granted time beyond the server window; 0 sustained worker backlog or DB deadlock failures. For normal online requests, target p95 response ACK ≤ 2 s, p99 ≤ 5 s; p99 entry/bootstrap ≤ 5 s excluding documented queue wait; p99 usable handoff ≤ 5 s after authoritative transition; p99 terminal result available ≤ 30 s. A bounded 429 with valid retry guidance is not a failure if the eligible student is admitted within the configured check-in window. Report every tail miss, not only averages. Adjust latency budgets only by an approved, documented product requirement before testing.

Repeat the complete run after any capacity fix. Run at least one 30-minute post-exam observation window to catch late workers, duplicate materialization, and memory/connection leaks. A report must include raw per-student verdicts, aggregate metrics, fault timestamps, infrastructure configuration, and a list of every mismatch/pending case.

## 6. Existing coverage to reuse, and gaps to close

- Reuse `e2e/sat-transition-flow.spec.ts`, `e2e/sat-timing-contract.spec.ts`, `e2e/sat-answer-recovery.spec.ts`, `e2e/sat-auto-resume.spec.ts`, and `e2e/sat-product-workspace.spec.ts` as small-scale browser/integration baselines. Reuse `backend/go/integration/sat_adaptive_routing_test.go` and `backend/go/integration/sat_response_durability_test.go` for real-DB boundary assertions. Run with Bun/Go as specified by the repo; preserve their logs in the rehearsal report.
- The current `k6/prod-exam-day.js` and `k6/README.md` describe an **IELTS-oriented** API load flow. `k6/scale-proof/*` proves selected entry/bootstrap/save/poller/staff seams at smaller or simulated scales. Neither is evidence for a full published-duration, 10,000-student SAT run. Implement a SAT-specific distributed k6 scenario using the real SAT V2 bootstrap, module, response, routing, and completion paths, and pair it with sampled real browsers and the all-student DB/result comparator.
- The current SAT browser suite expects an offline page reload to fail (`e2e/sat-product-workspace.spec.ts`). Test the supported behavior honestly: loaded-page offline work and outbox reconciliation, plus online recovery after reload/crash. If product requirements promise recovery of local-only answers after an offline crash, add and pass that separate test before claiming it.
- Verify the **server-owned cohort timing model** directly: compare the student's displayed module time, proctor roster module/section time, delivery bootstrap, and database deadline at the same server revision. In `cohort_section_v3`, late entry is clamped to the room window; pause/extension freezes or changes time only through server commands. Browser clock skew, stale bootstrap, or reconnect must never override it.
- Confirm the actual server admission rule at runtime start, during a module, during the gap, and after completion. Current entry UI allows registration before the proctor starts; test the later cases through both the API and UI and record the server's decision and remaining time.

## 7. Execution order and sign-off

1. Freeze the published SAT version, schedule/runtime timing model, admission/recovery rules, answer-oracle format, and numerical latency budgets. Derive expectations from that product configuration.
2. Run focused backend and Playwright tests, then a 25-student room, 500 students, 2,000 students, and the full 10,000-student rehearsal. At each step, run the same answer comparator and stop on a correctness failure before increasing load.
3. Run a second full-size rehearsal with injected failures for the full configured duration (144 minutes for the current default fixture). Compare 100% of admitted attempts against their journals after reconciliation; manually inspect representative higher/lower, offline, browser-crash, late, and pending-submission cases.
4. Sign off only with the pinned build/fixture IDs, configuration snapshot time, full per-student verdict file, load dashboard/export, zero-blocker defect list, and named owner for any supported pending-submission recovery. Any `unverifiable`, mismatched, missing, or wrong-branch student is a failed release gate.
