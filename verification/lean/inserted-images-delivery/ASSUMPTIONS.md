# Assumptions and unknowns

Each assumption names the real-world owner of the fact, the code/DB anchor it
rests on, how it can be validated, and how critical it is to the proof.

| ID | Assumption | Owner / anchor | Validation | Criticality |
| --- | --- | --- | --- | --- |
| A1 | `getImageUrlCandidates` returns `[]` for a whitespace-only URL and for `javascript:`/`vbscript:`/`data:text/html` URLs, and otherwise returns a non-empty list (the four Drive forms for a Drive share link, else the raw URL). | `src/utils/imageUrl.ts` (`UNSAFE_IMAGE_URL_PATTERN`, `isUnsafeImageUrl`, `getImageUrlCandidates`) | Reviewed source + `src/utils/__tests__/imageUrl.test.ts`; modelled as the `blank`/`unsafeScheme`/`drive`/`plain` classes in `Model.lean`. | High — R5 and every placement theorem are stated over this partition. |
| A2 | A React/DOM key token built from `(id, position)` is unique per rendered sibling when positions are `0…n-1`; an id-only token collides on repeated ids. | React reconciler; anchor `src/components/student/StudentInsertedImages.tsx` (key construction) | Empirical: the discriminating test fails under an id-only key and passes under the position-suffixed key (`evidence/focused-suite.txt`). | Medium — drives R7; the failure mode is a warning plus unstable reconciliation, not data loss. |
| A3 | `StudentQuestionBlockSection` is the single delivery frame for IELTS blocks, so one insertion point covers reading, listening, science, runtime preview and review. | `src/components/student/StudentQuestionPanel.tsx` → `StudentQuestionBlockSection`; `StudentReading`, `StudentListening`, `StudentScience` all pass `renderBlockInstruction` into the same section component | Reviewed call graph; the delivered-frame tests mount the section directly. | High — the fix's coverage claim rests on this. |
| A4 | The backend stores `exam_versions.content_snapshot` as opaque JSON and the delivery read returns it unchanged, so `insertedImages` reaches the browser. | `internal/exams/service.go` (raw `content_snapshot` insert/select), `internal/student/service.go` (`json.RawMessage`), `internal/act/service.go` (question keys copied wholesale, `science` key preserved) | Reviewed SQL/Go source; no field-level whitelist exists on the IELTS path. | High — if a backend compaction dropped the field, the client fix would be moot for those rows. |
| A5 | `hydrateExamState` spreads the incoming snapshot over a fallback (`{...fallback, ...partialState}`), so a present `insertedImages` survives hydration. | `src/services/examAdapterService.ts`; `normalizeQuestionBlock` only rewrites `DIAGRAM_LABELING` image URLs and `SINGLE_MCQ` stems/options | Unit test `preserves block inserted images through delivery hydration` (`evidence/focused-suite.txt`). | High — this is the data path the preview uses. |
| A6 | A blank instruction renders no instruction element in listening (`renderBlockInstruction` returns `null`) while reading always renders the box; images must precede content in either shape. | `src/components/student/StudentListening.tsx` (`renderBlockInstruction`), `StudentReading.tsx` | Reviewed source; modelled as `frameSlotsNoInstruction` with R2 proved for it. | Medium — R2 exists only because of this divergence. |
| A7 | The `insertedImages` shape is `{ id, url, caption }` rows, and `coerceInsertedImages` can produce repeated ids when a payload repeats them (e.g. an imported workbook). | `src/types.ts` (`InsertedBlockImage`), `src/utils/insertedImages.ts` | Reviewed source; the duplicate-id witness in `Counterexamples.lean` mirrors that shape. | Medium — it is the precondition of the R7 hazard. |

## Unknowns (recorded, not assumed)

| ID | Unknown | Why it matters | How to resolve |
| --- | --- | --- | --- |
| U1 | Whether every authored Drive URL is actually fetchable by a student browser (link sharing, Google throttling, corporate proxy). | The model proves *placement and provenance*, never that pixels appear; a private Drive file still fails to load, and the candidate chain can exhaust. | Browser check against real shared links; Drive audit of the exam's assets. |
| U2 | Whether the installed Drive candidate order (thumbnail → lh3 → uc → usercontent) is the most reliable in the deployed regions. | Affects perceived load success, not correctness of placement. | Field telemetry on image load failures; revisit candidate order. |
| U3 | Whether published versions already in the database contain `insertedImages` that authors expect to see. | The fix is client-side, so previously published content starts rendering after deploy — intended, but it is a visible behaviour change on existing exams with no migration. | Query published `content_snapshot`s for the field before rollout. |
| U4 | Whether layout of a large diagram inside the question pane (rather than the material pane) matches staff expectations for listening. | The slot is fixed by the editor's own copy; visual acceptance is untested. | Visual review with an author on a real exam. |
| U5 | Whether SAT/ACT-delivered content model will later gain an inserted-image concept. | If it does, `SatQuestionRenderer`/`ExamQuestionRenderer` would need the same slot. | Re-run this engagement if the SAT content model adds the field. |
