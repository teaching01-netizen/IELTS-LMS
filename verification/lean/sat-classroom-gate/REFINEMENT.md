## Transaction and crash boundaries

The actual `CreateRoom` transaction claims a receipt, may seal a draft, creates the backing schedule, calls `PersistSATSession`, inserts the link and roster, then stores the response snapshot. If the Classroom gate returns an error after an earlier draft seal or schedule insert, `WithTx` returns before commit and deferred rollback runs. `PublishEmission.Flush(err)` does not publish success telemetry on that path. This source path is coherent with the atomic model; only a real supported-database run can validate triggers, transaction semantics, and durability.

A crash before commit must leave no receipt/effect; a crash after commit but before the client receives the response must be recovered by the same operation key. These are database/API refinement obligations, not Lean conclusions.
