## Explicit model restrictions

- Lean `Initial` assumes the same budget, waiter, worker-count, and runtime-plan predicates later called `Invariant`; `emptyState_initial` proves only the selected empty state belongs to it. It does not establish that arbitrary database startup/restore state is valid.
- `Operational.State` models aggregate pending/failure counts, waiters, active start workers and a configurable worker limit, one initializer flag, process state, and a pinned runtime version. It omits individual wait records, timestamps/deadlines, DB rows, request/ACK histories, SQL errors, caches, and table-level lock schedules.
- `Operational.Step` is a pure deterministic state transition, with arbitrary finite interleavings from its action type. The worker-count theorem is an abstract semaphore-bound property; it does not model Go goroutine scheduling, starvation, or DB-pool initialization. DB transaction atomicity and rollback remain abstractions.
- No fairness, availability, retry-success, timing, or performance premise is used; no liveness/capacity theorem is claimed.
